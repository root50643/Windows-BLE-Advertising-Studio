# Protocol research and evidence boundaries

## Apple

Reference: OpenHaystack firmware at
[`ea05dadb9e6e71075ef08afb5c2087302fbb7210`](https://github.com/seemoo-lab/openhaystack/blob/ea05dadb9e6e71075ef08afb5c2087302fbb7210/Firmware/ESP32/main/openhaystack_main.c).
The implemented reference AD structure is 31 bytes: length/type, Apple company
ID, subtype 0x12, subtype-length 0x19, state, 22 public-key suffix bytes, two high
bits, and hint. A 28-byte public-key x coordinate supplies the missing first six
bytes through a static-random address with top bits forced to 11. Given a
captured static-random address, the library can reconstruct that x coordinate.
This is structural parsing, not curve membership or identity authentication.

Windows cannot set that address. The candidate now allows 31-byte controlled legacy submissions with a warning above the conservative 28-byte threshold. A manufacturer-only transmission in extended mode would still
not reproduce the reference transport or establish Apple compatibility.

## Google

Primary reference: [FHN v1.3 specification](https://developers.google.com/nearby/fast-pair/specifications/extensions/fmdn).
Secondary implementation reference reviewed:
[GoogleFindMyTools at 660be5395702ff7f1a6174f4ec4c865a57c7b527](https://github.com/leonboe1/GoogleFindMyTools/tree/660be5395702ff7f1a6174f4ec4c865a57c7b527).

The preview encodes flags 0x06 and service data AD 0x16 with UUID bytes AA FE,
frame 0x40/0x41, 20-byte or 32-byte EID and optional hashed flags. The parser
accepts both widths and flags presence, distinguishes other FEAA/Eddystone
frames, and does not claim to authenticate an EID or decode hashed flags without
the scalar. The research preview uses precomputed EIDs; the Tracker page separately derives secp160r1 EIDs with AES-256 and Bouncy Castle. The secret EIK is never
treated as an EID and is not placed into a payload by the preview.

Exact frames remain blocked by Publisher's reserved flags and service-data rules; the separate GATT backend tests ServiceData and treats incomplete advertising as failure. The candidate adds owned-account registration and report retrieval via a self-hosted provider. Fast Pair accessory certification, address synchronization, ringing and DULT remain outside the implementation. A format
preview does not produce an accessory visible in the official Find Hub app.

## Controlled test procedure

1. Use owned/authorized devices and informed participants. Acknowledge consent.
2. Create independent profiles and independent key references.
3. Inspect generated bytes and Windows validation before any transmission.
4. Use supported generic manufacturer data to test the radio path first.
5. Limit research transmissions to 1–300 seconds, with visible Stop controls.
6. Import an independently obtained AD capture and its source/time/address using
   `external-observation.example.json` as the schema. The sample is explicitly
   an example and is not evidence of a capture performed by this project.
7. Compare bytes and review protocol/address constraints separately. Preserve
   the distinction between API Started, RF evidence, protocol compatibility and
   a network location report. No location report was retrieved by this project.

Comparison uses exact AD-byte order. Windows-added flags or reordered sections
can produce a mismatch even when some payload fields are shared. A user-imported
capture is evidence supplied by the user; provenance is not authenticated here.
